# 逆引き（性質から候補を絞り込む）の設計

organic-reaction-map.html に実装した逆引きモードの記録と、その骨格を
他の教材に持っていくための整理。第1部は有機での実装そのもの、第2部は
化学の中身を抜いた型、第3部はアミノ酸マトリクスへ当てる際のメモ。

---

## 第1部: 有機反応系統図での実装

### 1-1. 入力条件

対象は 47 化合物（`data/organic-properties.json`）。条件スロットは検査 9 種と分子式 1 つで計 10。

| # | 条件 | UIラベル | kind | 選べる値 |
|---|---|---|---|---|
| 1 | `naoh_soluble` | NaOH水溶液に溶ける | bool | 未検査 / 陽性 / 陰性 |
| 2 | `nahco3_reaction` | NaHCO3からCO2が発生 | bool | 未検査 / 陽性 / 陰性 |
| 3 | `hcl_soluble` | 塩酸に溶ける | bool | 未検査 / 陽性 / 陰性 |
| 4 | `iodoform` | ヨードホルム反応 | bool | 未検査 / 陽性 / 陰性 |
| 5 | `silver_mirror` | 銀鏡反応 | bool | 未検査 / 陽性 / 陰性 |
| 6 | `fehling` | フェーリング液の還元 | bool | 未検査 / 陽性 / 陰性 |
| 7 | `fecl3` | 塩化鉄(III)の呈色 | color | 未検査 / 陽性 / 陰性 |
| 8 | `bromine_water` | 臭素水 | enum | 未検査 / 脱色 / 白色沈殿 / 反応なし |
| 9 | `bleaching_powder` | さらし粉の呈色 | color | 未検査 / 陽性 / 陰性 |
| 10 | 分子式 | 分子式 | text | 空 または完全一致文字列 |

kind の役割は、JSON の生の型を「結果値」に正規化する点だけにある。

- `bool` — `true`→`陽性`、`false`→`陰性`
- `color` — 色名の文字列。空文字でなければ `陽性`、空文字なら `陰性`。原文（`紫色`／`赤紫色`）は 1 件確定時の詳細表示にだけ出す
- `enum` — JSON の値そのものが結果値。表示ラベルだけ差し替える（値 `なし` → 表示「反応なし」）

分子式は `String(s).replace(/\s+/g,'')` で空白を落とすだけ。大文字小文字は区別する。前方一致も部分一致もしない。

**逆引きで使っていないフィールド**: `acidity`、`molecular_weight`、`functional_groups`、`distinguishing`、`confidence`。前 4 つは 1 件確定時の詳細に出るだけで絞り込みには効かない。`confidence` は埋め込み JSON の中にあるがコードから一度も参照していない。系統図モード側にある官能基フィルタは `node.group`（アルコール・アルデヒド等の分類）を見ていて、`properties.functional_groups` とは別物。**逆引きモードに「官能基から絞り込む」条件は存在しない**（タスクの想定条件に「官能基」が含まれていたが、実装の実態を優先してここに明記する）。

### 1-2. 組み合わせ方

純粋な AND。部分一致も、match の強さの段階も無い。

```
matches(p, skipTest, skipFormula):
  for t in TESTS:
    if t.id == skipTest: continue
    if rev.tests[t.id] !== null かつ outcomeOf(t,p) !== rev.tests[t.id]: return false
  if !skipFormula かつ rev.formula かつ p.molecular_formula !== rev.formula: return false
  return true
```

`null`（未検査）はその条件の評価を丸ごと飛ばす。「未検査」は「陰性」ではない。

`skipTest` / `skipFormula` は「その 1 条件だけ外して数え直す」ための引数で、次の 2 か所が使う。

- 0 件のときの緩和候補
- 1 件確定時に「検出反応だけで決まったのか、分子式まで要ったのか」を分ける

描画のたびに 2 つの集合を出す。

- `all` = 10 条件すべて
- `det` = 分子式を外し、検出反応 9 つだけ

### 1-3. 識別の限界を先に計算しておく

9 検査の結果ベクトルを `|` 連結したキーで 47 件をグループ分けし、`PROFGRP` に持つ。起動時 1 回だけ。

実データでは 13 クラスに割れる。内訳は 27 / 5 / 3 / 3 / 1×9。つまり検出反応 9 つを全部やっても一意に決まるのは 9 件だけで、残り 38 件は原理的に区別できない。最大クラスの 27 件は「9 検査すべて陰性」の集団。

この事前計算があるので、1 件に絞れたときに「その 1 件は本当に決まったのか、たまたま他の条件で切れただけか」を言い分けられる。

### 1-4. 候補 0 件のときの画面

`revverdict` に `.hint.warn`（左ボーダー マゼンタ）のブロックを 1 つ出す。

```
候補なし
この条件をすべて満たす化合物は、このデータの47件の中には無い。
次のどれか1つを外すと候補が出る。
・銀鏡反応（陽性） を外す → 4件
・分子式 C2H4O を外す → 2件
```

- 選択済みの条件を 1 つずつ外して `listOf` を再実行し、1 件以上残るものだけ列挙
- 残り件数の降順（外したときに候補が広く戻るものが上）
- どれを 1 つ外しても 0 のままなら「条件を1つ外しただけでは候補は出ない。2つ以上外す必要がある。」に差し替え
- 候補リスト（`candlist`）は全件 `display:none` になるので空欄になる。COMPOUND カードは `hidden`
- NEXT STEP カードは `cands.length <= 1` で `hidden` になるため、0 件時は消える

### 1-5. 候補が複数残っているときの画面

**件数**: `候補 12 / 47　　条件 2 件` を Mono・`aria-live="polite"` で常時表示。分母は総数 47 固定、「条件」は選択済みスロット数（分子式が入っていれば +1）。

**リスト**: 47 件ぶんのボタンを起動時に一度だけ生成し、以後は `.gone`（`display:none`）の付け外しで見せ隠しする。DOM を作り直さない。

- 並び順は `PROPS.properties` の配列順で固定。絞り込んでも並び替えない。同じ化合物が同じ位置に居続けるので、条件を足したときにどれが消えたか目で追える
- 1 行 = 名前 / 示性式（Mono・青）/ 2 行目に分子式と官能基
- 消える行は 180ms かけて `opacity:0` にしてから `display:none`。`prefers-reduced-motion: reduce` なら即座に消す
- クリックで `gotoMap(id)` — 系統図モードへ移り、その化合物を選択状態にする

**まだ何も選んでいないとき**: 47 件が全部並んだ状態で「まだ何も検査していない。上の検査を選ぶか、分子式を入れると絞り込まれる。」を出す。

**NEXT STEP（次の一手）**: 未検査の各条件について、現在の候補を結果値でビン分けする。

- `worst` = 最大ビンの件数、`split` = ビンの数
- `worst` 昇順、同数なら `split` 降順で並べる。ミニマックス（結果がどちらに転んでも候補が少なく残る順）
- `split <= 1`（全候補が同じ結果になる）は `.sug.flat` でグレーにし「この検査では絞れない」と出す
- 定義した選択肢に無い結果値がデータに現れても行を落とさない保険が入っている

### 1-6. 1 件に絞れたときの画面

候補リストの当該行に `.solo`（左 3px 緑ボーダー + 260ms の背景フラッシュ）を付け、右カラムに COMPOUND カードを開く。カードは 3 段。

**(a) 何で決まったかの判定**

| 条件 | 表示 |
|---|---|
| `det.length === 1` | `.hint.ok`「検出反応だけで決まった」 |
| `det.length > 1` | `.hint.warn`「分子式まで使って決まった」＋ 分子式を外すと残る化合物名（8 件で打ち切り「ほかN件」） |

**(b) 等価クラスの警告**

`PROFGRP` のクラスサイズが 2 以上なら、分子式で切れていても必ず出す。

```
この検査の組み合わせでは他にも該当がある
アセトンは、この9つの検出反応の出方が エタノール・2-プロパノール と完全に同じ。
検出反応をこれ以上増やしても、この3件は区別できない。
分子式・分子量・官能基で見分けることになる。
```

**(c) 詳細**: 名称・示性式・タグ（系統／分類／酸性度）・分子式・分子量・官能基・9 検査の出方一覧（color は原文の色名、未呈色は「呈色しない」）・`distinguishing`・系統図へ飛ぶボタン。

### 1-7. モード切り替え

カード 1 枚に 2 ボタン。

```html
<button class="btn on" id="m-map" aria-pressed="true">系統図から見る</button>
<button class="btn"    id="m-rev" aria-pressed="false">性質から化合物を絞り込む</button>
```

`setMode(m)` が `view-map` / `view-rev` の `hidden` を反転し、両ボタンの `.on` と `aria-pressed` を同時に更新する。逆引きへ入るときだけ `revRender()` を呼ぶ。逆引きの状態（選んだ検査・分子式）はモードを往復しても保持される。

逆→順の遷移 `gotoMap(id)` は、系統図側のフィルタが効いていると目的の化合物が非表示で選べないため、`groups` / `types` / `detectOnly` / `pathMode` / 経路 / 選択をすべて解除してからチップを組み直し、`pickNode(id)`、ビューポートをその座標へ中央寄せ、ノードに `focus()` する。

### 1-8. 幅 375px とキーボード

**レイアウト**

- `.revgrid` は既定 1 カラム。761px 以上で `minmax(330px,40%) / minmax(0,1fr)` の 2 カラム。375px では TESTS → NEXT STEP → CANDIDATES → COMPOUND の縦 1 列
- 430px 以下で `.tlab{flex:1 1 100%}`。検査名が行全体を占め、選択肢ボタンが次の行に落ちる。ボタンは 10.5px / `min-width:35px` / `padding:3px 6px`
- 最も広い行は臭素水の 4 ボタン（未検査 / 脱色 / 白色沈殿 / 反応なし）で、実測でカード内幅に収まる
- 分子式入力は 430px 以下で `width:112px`。ラベル・入力・リセットボタンが `.fxrow` の `flex-wrap` で折り返す
- 候補行は `padding:6px 8px` の 1 行 + 2 行目。タップ高さは約 44px

**キーボード**

- 操作要素はすべて `<button>` と `<input type=text>`。独自のキーハンドラは無い
- フォーカスリングは `.btn:focus-visible` / `.cand:focus-visible` / `.fx:focus-visible` で `outline:2px solid var(--c2)`
- 検査 1 行は `role="group"` + `aria-label="◯◯ の検査結果"`。各ボタンに `aria-label="◯◯ 陽性"` と `aria-pressed`
- 絞り込みで消えた候補は `display:none` なのでタブ順から自動的に外れる。残った件数ぶんだけを Tab で辿れる
- 候補件数は `aria-live="polite"` で読み上げられる
- 系統図モードにあるノードの矢印キー移動（roving tabindex）は逆引きモードには無い。検査ボタンは Tab 送りのみ

**未達**

- `revverdict`（0 件警告・確定判定）は `aria-live` ではない。件数は読み上げるが、警告文そのものは読み上げられない
- フェードアウト中の 180ms、消えかけの候補が一時的にフォーカス可能なまま残る

## 第2部: 型として再利用できる部分

以下に化学の語は出てこない。N 個の候補を M 個の条件で絞る、という問題として書く。

### 2-1. 問題の形

- 候補集合 `items`（N 個）
- 条件定義 `conds`（M 個）。各条件は「候補を受け取って、有限個の結果値のどれか 1 つを返す関数」を持つ
- 利用者の入力は条件ごとに `null`（未入力）または結果値のどれか 1 つ

### 2-2. 正規化を 1 か所に閉じ込める

候補データの生の型は条件ごとにバラバラでよい（真偽値・自由文字列・列挙・数値）。それを吸収する関数を 1 本だけ置き、以降のコードは正規化後の結果値しか見ない。

```
outcomeOf(cond, item) -> 結果値（文字列）
optionsOf(cond)       -> [[結果値, 表示ラベル], ...]
```

これを入れておくと、
- 絞り込み・次の一手・等価クラス・UI 組み立てがすべて同じ 1 本を通る
- 自由文字列を 2 値に潰しても、原文は詳細表示に残せる（潰すのは判定用、見せるのは原文）
- 結果値と表示ラベルを分けているので、内部値をデータのまま保ちながら日本語ラベルだけ変えられる

### 2-3. 絞り込み本体は skip 引数つきで 1 本だけ書く

```
matches(item, skipCond) =
  すべての cond について（skipCond は飛ばす）
    入力が null → 通す
    入力 === outcomeOf(cond, item) → 通す
    それ以外 → 落とす

listOf(skipCond) = items.filter(i => matches(i, skipCond))
```

AND のみ。スコアも重みも部分一致も入れない。`skipCond` があるので、

- 0 件時の「どれを外せば戻るか」
- 確定時の「その条件が無くても決まっていたか」
- 条件群を 2 系統に分けた並行集合

がすべてこの 1 本の呼び分けで済む。フィルタ関数を用途ごとに増やさない。

### 2-4. 結果値が二値で割り切れないときの受け方

「二値で割り切れない結果」への対処は、性質として 3 通りに分けられる。

**(A) 多値化する** — 二値に丸めず、結果値を 3 つ以上そのまま持つ。UI のボタンも 3 つ以上並ぶ。絞り込みも次の一手も等価クラスも、結果値が何個あろうと同じコードで動く（結果値でビン分けしているだけ）。単純に「3 通り目の確定した結果がある」場合はこれでよい。

**(B) 判定用に潰し、表示用に原文を残す** — 自由文字列を「該当あり／なし」の 2 値に正規化して絞り込みに使い、詳細表示には元の文字列を出す。情報を捨てずに判定だけ単純化する型。

**(C) 未定義の結果値を落とさない** — 定義済みの選択肢に無い結果値がデータに現れても、集計側は実データのキーを走査して拾い、UI に追記する。データを増やしたときに黙って行が消えるのを防ぐ。

**(A)〜(C) では対処できない場合がある**: 候補の性質そのものが「観測条件によって陽性にも陰性にもなりうる」場合（=「条件付き」の結果）。この場合、その候補を安易に多値化（A）で切り離すと、利用者が能動的に「条件付き」を選ばない限り絞り込みから排除され続けてしまう。設計としては次の 2 択になる。

1. 利用者が選べる選択肢は変えず（例: 陽性／陰性の 2 つ）、「条件付き」の候補は入力がどちらであっても両立するとみなして残す：
   `通過条件 = (outcomeOf(cond, item) === 入力) || (outcomeOf(cond, item) === '条件付き')`
   理由: 観測結果が陽性であれ陰性であれ、「条件付き」の候補はどちらの観測とも矛盾しない。絞り込みで排除してはいけない。
2. 利用者も「条件付き」を選べる 3 値にする（= (A) の多値化そのもの）

**1 を採る場合の注意**: 絞り込みの通過条件と、識別力の計算（2-5）を同じ関数で扱ってはいけない。1 の分岐は「通すが、区別できたことにはしない」という非対称を作る。等価クラスのキー生成では「条件付き」を独立した第 3 の値として扱う（＝陽性グループにも陰性グループにも混ぜない）。混同すると、「条件付き」の候補が実際には両方のグループと区別できていないのに、どちらか一方のクラスに紛れ込んで「区別できた」と誤って計算されてしまう。

候補が「条件付き」のおかげで残っている場合は、候補一覧のその行に理由を注記する（例:「この反応の出方は条件による」）。黙って残すと、利用者は自分の入力ミスだと誤解する。

### 2-5. 識別の限界を起動時に 1 回だけ計算する

全条件の結果ベクトルをキーにして候補をグループ分けし、保持する。

```
key(item) = conds.map(c => outcomeOf(c, item)).join('|')
```

これで「この条件セットでは何クラスまでしか割れないか」「どの候補とどの候補が最後まで区別できないか」が事前に分かる。教材としてはこれがいちばん効く。1 件に絞れたとき「条件を足せばもっと分かる」のか「これ以上は原理的に無理」のかを言い分けられるのは、この事前計算があるから。

2-4 で「条件付き」を扱う場合は、この `key()` の中で「条件付き」を独立した値として扱うこと（2-4 参照）。

計算量は N×M で、N が数十なら起動時に一度回して問題ない。

### 2-6. 条件を 2 系統に分けて並行に数える

**この型は、条件セットに自然な非対称分割（少数だが決定力の強い条件 vs 多数だが決定力の弱い条件）が存在する場合にのみ使う。すべての問題がこの形に分かれるとは限らない。無理に当てはめない。**

条件のうち「本筋の条件群」と「答えを直接指す強い条件」を分け、2 つの集合を毎回出す。

- `all` = 全条件をかけた集合
- `core` = 強い条件を外し、本筋の条件だけの集合

`all` が 1 件でも `core` が 2 件以上なら「強い条件のおかげで決まった」と言える。学習者に「本筋の条件だけではどこまで詰められたか」を返すための仕掛け。

### 2-7. 次の一手（ミニマックス）

未入力の各条件について、現在の候補を結果値でビン分けする。

- `worst` = 最大ビンの件数（最悪ケースで残る数）
- `split` = ビンの数

`worst` 昇順、同数なら `split` 降順。`split <= 1` は「この条件では絞れない」と明示してリストに残す（隠さない）。

期待値ではなく最悪値で並べる。候補が均等に割れる条件が上に来て、めったに当たらない一撃必殺は下に沈む。

### 2-8. 3 状態の UI 原則

| 状態 | やること | やらないこと |
|---|---|---|
| **0 件** | 「この条件を満たすものは無い」と断言する。1 条件ずつ外して 1 件以上になるものを、戻る件数の降順で列挙する。どれを 1 つ外しても 0 なら「2 つ以上外す必要がある」と言う | 直前の入力を勝手に取り消す。空欄のまま放置する |
| **複数残存** | 残り件数と分母を常に出す（`n / N`）。入力済み条件の数も出す。**リストの並び順は初期順で固定し、絞り込みで並び替えない**。消える項目はフェードしてから消す（`reduced-motion` では即時）。次の一手を出す | 上位 n 件だけ見せる。件数を隠す。並べ替えて位置を動かす |
| **一意に確定** | その 1 件を強調する（一過性のアニメ + 恒常的な枠）。**何のおかげで決まったかを言う**（本筋の条件だけか、強い条件を使ったか）。**等価クラスが 2 以上なら必ず警告する**。「条件付き」のおかげで残った候補には理由を注記する（2-4）。詳細を開く。次の一手カードは畳む | 「正解です」で終える。等価クラスの存在を黙る |

**0 件と 1 件で最も重要なのは、どちらも「なぜそうなったか」を返すこと。** 件数だけを出す実装は、絞り込みの練習にならない。

### 2-9. アクセシビリティとモバイルの最低ライン

- 操作要素は素の `<button>` / `<input>` を使い、独自キーハンドラを足さない。Tab 順は DOM 順に従う
- 選択状態は `.on` クラスと `aria-pressed` を必ず同時に更新する。片方だけ更新しない
- 排他選択のボタン群は `role="group"` + `aria-label` で囲む。個々のボタンにも「項目名＋選択肢名」の `aria-label` を付ける（ボタン文字だけでは「陽性」としか読まれない）
- 残り件数の表示に `aria-live="polite"` を付ける。**0 件警告・確定判定の領域にも付ける**（有機の実装はここが未達 — 1-8 参照。転用時は同じ穴を空けない）
- 絞り込みで消す項目は `display:none` にする。`visibility` や `opacity` だけではタブ順に残る
- フェードアウトさせるなら、フェード中もフォーカス可能である点を許容するか、先に `tabindex=-1` を落とす
- `prefers-reduced-motion: reduce` でフェードと強調アニメを止める
- 375px で 2 カラムを 1 カラムに畳む。ラベルとボタン群が同一行に収まらない幅では、ラベルを `flex:1 1 100%` にして行を分ける
- ボタンの最小タップ寸法を確保する。文字を縮めるより行を折り返す
- 候補リストは全件を一度だけ生成し、以後はクラスの付け外しで見せ隠しする。再生成しない（フォーカスが飛ぶ、アニメが切れる）

- 通過条件: `outcomeOf(cond, item) === 入力 || outcomeOf(cond, item) === 'conditional'`

## 第4部: 候補がラベルの列である場合への一般化

第2部・第3部は候補が「1件・1つのラベル」である前提で書かれていた。候補が「固定長のラベルの列（並び）」になる問題に同じ型を適用した記録。第1部・第3部と違い、この節には化学の語を一切出さない。

### 4-1: 候補の形を変えても、型はそのまま通った

第2部が定義した型が要求しているのは次の2つだけである。

- 候補の集合 `items`（有限個）
- 条件 `cond` は「候補を受け取って、有限個の結果値のどれかを返す関数」

候補が単一のラベルであっても、固定長のラベル列であっても、この2条件さえ満たしていれば、絞り込み本体（2-3）・次の一手（2-7）・等価クラスの事前計算（2-5）・3状態のUI原則（2-8）はそのまま成立する。手を入れる必要があったのは「候補集合をどう列挙するか」（列挙の対象が単一の項目から、順列・組合せの列挙に変わった）と「条件が候補から結果値を取り出す関数の中身」（列の一部を切り出す・並び順を無視した多重集合に潰す、といった候補の内部構造に踏み込んだ処理が増えた）の2箇所だけで、絞り込み・次の一手・等価クラスという骨格そのものには一切手を入れていない。

「候補が構造的に何であるか」を型の外側に出し切ってあったことが、候補の形をまるごと差し替えても型を壊さなかった理由である。

### 4-2: ラベルの性質を外部テーブルに追い出し、判定ロジックから中身を追い出す

第2部 2-2（`outcomeOf` / `optionsOf` への正規化の一本化）をさらに一段推し進めた形。候補がラベルの列になったことで、条件の判定は「列全体の形」だけでなく「列を構成する個々のラベルの性質」（属性ごとの数値・真偽値）を参照する必要が出てくる。この性質の値そのものを、判定ロジックの外側から渡す1つの引数（ラベルごとの属性テーブル）にまとめ、絞り込み・次の一手・等価クラス・生成のどの処理にも、性質の中身を直接書き込まなかった。

判定ロジック側が知っているのは次の3つだけである。

- 候補は「ラベルの列」である
- 条件は「型（種類）」と、型ごとに決まった少数のパラメータ(位置・長さ・比較対象のラベル集合など)を持つ
- ラベル1つぶんの性質を知りたいときは、外から渡された属性テーブルを素通しで引く

属性テーブルの中身が「何を表す値か」は判定ロジックにとって完全に不透明で、ラベルをキーにした対応表でしかない。この結果、絞り込み・次の一手・等価クラス・生成のどの行にも、ラベルの意味を知っている行が1つも無い状態を保てる。属性テーブルの中身をまるごと別の性質に差し替えても、判定ロジック本体は1行も変えずに動く。2-2 が「結果値の正規化」を1箇所に閉じ込めたのに対し、こちらは「判定材料そのものの中身」を丸ごと外に出した形になる。

### 4-3: 分離型と完了型は別物であり、成立する場面が逆になる

「残り候補を1件に絞る条件を探す」処理には、性質の異なる2つの型がある。

**分離型**: 残っている候補全員に、まだ選んでいない条件を仮に当てはめたとき、全員が「別々の」結果値に散らばる条件を探す。各候補が「自分自身が正解だったら返るはずの結果値」を仮に計算し、重複が無いかを見るだけなので、正解を知らなくても計算できる。

**完了型**: 実際の正解から、その条件の観測値を1つ取り出し、その観測値1つで残り候補を絞ったときに1件になる条件を探す。正解（観測値そのもの）に依存する分、要求している条件はゆるい。残り候補全員が別々の値に散らばっている必要はなく、「今回はたまたま1件に絞れた」だけで成立する。

この2つは、成立しやすい場面が逆になる。

- 候補が少なく、条件の取りうる結果値の種類が多い(候補数以上に値の種類がある)場面では、分離型が成立しやすい。各候補が互いに違う値を取る余地が十分にあるため。
- 候補が多く、条件の取りうる結果値の種類が少ない場面では、分離型は鳩の巣原理により原理的にほぼ成立しない。値の種類が2つしかない条件(二値の条件)で、残り候補が3件以上あれば、全員が別々の値に散らばることは構造上不可能である。この場面で候補を1件に絞れるとしたら、それは「今回の観測値がたまたま偏っていた」という完了型の成立でしかありえない。

値の種類が2つしかないような条件を分離型の探索対象に含めても、候補が3件以上残っている限り原理的に「該当なし」を返し続けるだけの計算になる。分離型は値域が広い条件でしか意味を持たず、完了型は値域の広さに関係なく成立しうる。両者を使い分けるべき基準は「値域の広さ」であり、値域の狭さが分離型の不成立をほぼ決定づける。

### 4-4: 定義域だけを決める条件は、絞り込みからも「落とせる条件」の判定からも外す

条件の中には、候補を絞り込む判定材料には一切ならず、候補集合そのもの(定義域)を宣言するためだけに存在するものがある。この種の条件を判定関数にそのまま通すと、常に「真」を返す(=絞り込みに何の影響も与えない)実装になるのが自然だが、そう作った瞬間に副作用が生まれる。「不要な条件を検出して間引く」処理(ある条件を1つ外してみて、それでも候補が1件に絞れるなら、その条件は無くても良かったと判断して除く)が、常に真を返すこの条件を「外しても結果が変わらない=不要な条件」と誤判定し、間引いてしまう。

定義域を決めるだけの条件は、この間引きの対象から確実に除外しておく必要がある。ここで避けるべきなのは、条件の「見た目のパラメータ」(判定の粒度や公開範囲を指定する値など)を見て、保護するかどうかを分岐させる実装である。同じ種類の条件でも、パラメータの取り方によって「定義域を決めるだけ」の場合と「実際に絞り込みに効く」場合の両方がありうるなら、パラメータの値を見て保護対象かどうかを決める実装は、パラメータの取り方が増えるたびに分岐を漏れなく足し続ける必要が生じ、1つでも書き漏らせば、その組み合わせのときだけ誤って間引かれる。

安全なのは、条件の「種類(型)」そのもので保護するかどうかを決めることである。「この型の条件は、パラメータが何であれ常に定義域を決めるだけの条件である」と設計しておけば、パラメータの取り方が将来いくら増えても、保護の判定を書き足す必要がない。パラメータの値を見て判定を分岐させるのは、型による判定がそもそも成立しない(同じ型の中に「定義域を決めるだけ」のものと「絞り込みに効く」ものが混在する)場合の次善策として扱うべきで、既定の実装として選ぶものではない。
